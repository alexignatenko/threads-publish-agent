# Онбординг: настройка с нуля

Читай этот файл, когда `doctor` вернул код 3 (нет конфигурации) или код 4 (нет токена),
либо когда пользователь просит «настроить/подключить Threads».

Онбординг — это **разговор**, а не монолог. Задавай вопросы порциями по 2–4, ждите ответа,
не вываливай сразу двадцать. Всё, что можно узнать самому (версия Python, существующие файлы,
username аккаунта) — узнавай сам, не спрашивай.

Дальше `$T` = `python3 <SKILL_DIR>/scripts/threads.py`.

---

## Этап 1. Проверить окружение (сам, без вопросов)

```bash
python3 --version                 # нужен 3.8+
$T selftest                       # оффлайн-проверка скрипта, сеть не нужна
```

`selftest` должен вернуть `"ok": true`. Если нет — скрипт повреждён или Python слишком старый;
скажи об этом и останови онбординг. Внешних зависимостей нет, `pip install` не нужен.

Затем создай профиль и **сразу проверь, не передан ли токен уже**:

```bash
$T config init
$T auth status
```

Если в `auth status` поле `has_token` равно `true` — токен уже есть (чаще всего пользователь
положил его в переменную `THREADS_ACCESS_TOKEN`, это видно по полю `from_env`). Тогда не
спрашивай ни про приложение, ни про ключи: переходи сразу к
[короткому пути](#короткий-путь-токен-уже-есть).

Команда напечатает пути ко всем файлам профиля. Запомни их — дальше они понадобятся.
Если пользователь ведёт несколько аккаунтов Threads, каждый живёт в своём профиле:
`$T --profile brand config init`. Спрашивай про несколько аккаунтов только если пользователь
сам об этом заговорил.

## Этап 2. Объяснить, что понадобится, и выяснить, что уже есть

Скажи коротко и по делу примерно так:

> Чтобы публиковать в Threads, нужен доступ к официальному Threads API: приложение в Meta
> for Developers и токен доступа. Приложение создаётся один раз за 10–15 минут, дальше
> токен живёт 60 дней и продлевается автоматически. Всё делается бесплатно, своего домена
> и платных сервисов не нужно.

Скилл настраивает публикацию в **свой** аккаунт Threads. Если пользователь хочет публиковать
от имени посторонних людей — скажи честно, что это другой сценарий: он требует собственного
сервиса с веб-входом и проверки App Review у Meta, и скилл такого не делает.

Вопрос — один:

**«У тебя уже есть приложение Threads в Meta for Developers, или создаём с нуля?»**

- **Уже есть готовый токен** (пользователь говорит «токен у меня есть», «токен в переменной»,
  «возьми из другого сервиса») → [короткий путь](#короткий-путь-токен-уже-есть), минуя этапы 3 и 4.
- Приложение есть, токена нет → Этап 3, пункты 3–6. Пункт 3 не пропускай: у существующего
  приложения может не быть `threads_content_publish`, и тогда маркер выдастся, а публикация
  упадёт с 403 только на первом посте.
- Нет / не знает → Этап 3 целиком.

## Короткий путь: токен уже есть

Применяется, когда токен уже передан (в переменной `THREADS_ACCESS_TOKEN` или присланный
в переписке). Этапы 3 и 4 **пропускаются целиком**.

**Чего НЕ надо делать, даже если тянет:**

- не просить App ID, App Secret и Redirect URI — для чтения, публикации и продления готового
  токена они не нужны ни на одном шаге;
- не предлагать создать приложение в Meta;
- не вызывать `auth save-token`, если токен пришёл через `THREADS_ACCESS_TOKEN` — он уже
  виден скрипту, а сохранение положит его на диск, чего пользователь, скорее всего, не хотел;
- не решать за пользователя, продлевать токен или нет — об этом ниже отдельный вопрос.

**Что сделать:**

```bash
$T me
```

Покажи `username` и спроси, тот ли это аккаунт.

### Спроси про продление. Не решай за пользователя

Токен живёт 60 дней. Скилл умеет продлевать его сам, но продление выдаёт **новую строку**
токена — и если тот же токен работает в другом сервисе, там доступ может отвалиться.
Поэтому задай один вопрос:

**«Этот токен используется где-то ещё, кроме этого скилла — другой сервис, скрипт, бот?»**

**Ответ «да» или «не знаю»** → выключи продление и предупреди о ручном обновлении:

```bash
$T config set auth.allow_refresh=false
```

> Продление выключил, чужой сервис не задену. Обратная сторона: через 60 дней токен
> умрёт, и его придётся выпустить заново руками. Напомнить ближе к сроку я не смогу —
> скилл работает только когда ты меня позовёшь.

**Ответ «нет, только здесь»** → оставь продление включённым (это значение по умолчанию,
менять ничего не нужно) и предупреди в обратную сторону:

> Продление оставил включённым: скилл сам обновит токен, и вручную ничего делать не надо.
> Тогда не вставляй этот же токен в другие сервисы — после продления строка меняется,
> и у них отвалится доступ.

Чтобы продление действительно сработало, скиллу нужно знать срок жизни токена. У токена,
переданного через переменную или вставленного как есть, срока нет, и автопродление просто
не запустится. Проверь `expires_at` в `$T auth status`; если там `null`, сделай одно
из двух:

```bash
$T auth refresh --force      # вернёт новый токен с известным сроком на 60 дней
```

Команда требует, чтобы токену было не меньше 24 часов — только что выпущенный так продлить
не получится. Тогда остаётся обновлять вручную: раз в два месяца выпускать новый маркер
в генераторе. Скажи пользователю, что получилось, не придумывай.

### Если токен прислали в переписке

Сохрани его, не обменивая (обмен выпустил бы новую строку, а это как раз то, чего
на общем токене лучше не делать):

```bash
$T auth save-token --token <TOKEN> --no-exchange
```

Токен из переменной `THREADS_ACCESS_TOKEN` сохранять не надо — он уже виден скрипту.

Дальше — Этап 5.

Что ещё сказать пользователю, коротко:

- суточная квота (250 постов, 1000 ответов) общая на профиль Threads и делится со всеми
  приложениями; настоящий расход показывает `$T quota`;
- не менять Redirect URI и не отзывать доступ в настройках существующего приложения —
  это сломает сервис, который уже работает с этим токеном;
- если токен окажется без прав `threads_content_publish`, публикация вернёт 403 — тогда
  понадобится новый токен, и вот тут уже уместно предложить отдельное приложение Meta.

## Этап 3. Создать приложение в Meta for Developers

Это пользователь делает руками в браузере — ты не можешь сделать это за него. Дай ему
пошаговую инструкцию и дождись, пока он вернётся с токеном. Названия пунктов меню Meta
периодически меняет, поэтому описывай смысл шага, а не только точную надпись, и предупреди
об этом.

**Приложение здесь нужно только как контейнер**, через который Meta выдаёт доступ к своему же
аккаунту. Ни App ID, ни App Secret, ни Redirect URI для этого не понадобятся — не спрашивай их.

Инструкция для пользователя:

1. Открой <https://developers.facebook.com/apps> и войди под своим Facebook-аккаунтом.
   Если аккаунта разработчика нет, его предложат создать — это бесплатно.
2. **Create app**. В качестве цели (use case) выбери работу с **Threads API**
   (пункт называется примерно «Access the Threads API»).
3. Внутри приложения открой настройки Threads use case и добавь разрешения (permissions):
   - `threads_basic` — обязательно, без него не работает ничего;
   - `threads_content_publish` — обязательно для публикации;
   - `threads_read_replies` и `threads_manage_replies` — если планируешь отвечать в комментариях
     и скрывать спам;
   - `threads_manage_insights` — если нужна статистика.
4. На той же странице настроек найди раздел **«Генератор маркеров пользователя»**
   (User token generator) — он ниже полей с адресами. Нажми «Добавить аккаунт» и подключи
   свой аккаунт Threads.
5. Зайди в Threads → Настройки → Аккаунт → Сайты и приложения (Website permissions / Invites)
   и **прими приглашение**. Без этого API вернёт ошибку доступа.
6. Вернись в генератор маркеров и сгенерируй маркер. Это и есть токен, скопируй его.

**Поля с адресами на этой странице заполнять не нужно.** «URL обратного вызова для
перенаправления» и соседние поля относятся к входу через браузер, которого в этом сценарии нет.
Форма может не сохраняться без них — это не мешает генератору маркеров работать. Если
пользователь застрял на этой форме, скажи ему просто уйти с неё.

Два условия, о которых стоит предупредить заранее:

- **Аккаунт Threads должен быть общедоступным.** Для приватных аккаунтов маркер не выдаётся.
- **Режим разработки.** Пока приложение в нём, публиковать можно только в аккаунты, добавленные
  тестировщиками, то есть в свой. Для публикации от имени посторонних людей Meta требует
  App Review — это отдельная история, сейчас она не нужна.

## Этап 4. Сохранить токен

**Этот этап только для случая, когда токена ещё нет.** Если токен уже передан, ты здесь
по ошибке — вернись на [короткий путь](#короткий-путь-токен-уже-есть).

Маркер из генератора — уже долгоживущий, на 60 дней. Обменивать его не на что, ключи
приложения не нужны. Сохрани как есть:

```bash
$T auth save-token --token <TOKEN> --no-exchange
```

Дальше задай вопрос про продление и действуй по ответу — порядок описан в
[коротком пути](#спроси-про-продление-не-решай-за-пользователя). Токен из генератора
продлевается по самому токену, App Secret для этого не нужен.

### Проверка

```bash
$T me
```

Должен вернуться `id` и `username`. **Покажи username пользователю и спроси, тот ли это аккаунт** —
это единственный момент, когда ошибку в выборе аккаунта ещё можно поймать до публикации.

## Этап 5. Интервью о правилах публикации

Теперь — параметры поведения агента. Спрашивай порциями, предлагай разумный вариант по
умолчанию в каждом вопросе, чтобы пользователь мог ответить «давай как предлагаешь».

### Порция 1 — базовое

1. **На каком языке публикуем?** (по умолчанию — язык, на котором с тобой говорят)
2. **Часовой пояс?** (нужен для расписания; предложи угадать по контексту и подтвердить)

### Порция 2 — формат публикаций

3. **Кто может отвечать на посты?** — `everyone` (по умолчанию), `accounts_you_follow`
   (только те, на кого подписан), `mentioned_only` (только упомянутые).
4. **Как чаще подавать материал: одиночными постами или цепочками?**
   Объясни разницу: в Threads лимит 500 символов на пост, длинная мысль публикуется цепочкой —
   каждый следующий пост ответом на предыдущий. Варианты: «почти всегда одиночные»,
   «цепочки, когда мысль не влезает», «люблю цепочки-разборы». По умолчанию — второе.
5. **Оставлять ссылки в тексте или вложением?** Threads делает превью из первой ссылки в
   текстовом посте; можно задать её явно. Нужно знать, ставит ли пользователь ссылки вообще
   и не обрезает ли это охваты по его опыту.

### Порция 3 — комментарии

6. **Отвечать ли на комментарии под своими постами?** Варианты: «не лезь», «готовь ответы,
   я буду подтверждать» (по умолчанию), «отвечай сам на простое — благодарности, короткие
   вопросы — а спорное приноси мне».
7. **Скрывать ли спам и оскорбления?** (по умолчанию — приносить на подтверждение, не скрывать молча)

### Порция 4 — темп и подстраховка

8. **Сколько постов в день максимум?** (по умолчанию 10 — это локальный предохранитель,
   лимит самого API 250)
9. **Подтверждать каждую публикацию перед отправкой?** По умолчанию — да, и **не предлагай
   это отключать**. Если пользователь сам просит автопубликацию без подтверждения, предупреди,
   что посты нельзя ни исправить, ни удалить через API, и только потом меняй настройку.
10. **Есть слова и темы, которые нельзя публиковать никогда?** (клиенты, NDA, цены, политика —
    что угодно). Сложи их в стоп-лист.

### Записать ответы

```bash
$T config set \
  defaults.language=ru \
  defaults.timezone=Europe/Belgrade \
  defaults.reply_control=everyone \
  safety.max_posts_per_day=10 \
  safety.max_replies_per_day=50 \
  safety.require_yes_flag=true \
  safety.blocked_words='["нельзя_это_слово"]'
```

Значения с пробелами и списки передавай в кавычках; списки — как JSON. Ответы, которые не
ложатся в настройки (например, «цепочки только по вторникам»), записывай в `voice.md` —
ты будешь читать его перед каждым постом.

## Этап 7. Проверка и первый пост

```bash
$T doctor
```

Все проверки должны быть `ok: true`. После этого предложи:

> Давай проверим на живом посте. Я напишу короткий пост твоим голосом, покажу тебе текст,
> и опубликую только если скажешь «да». Удалить его через API потом не получится, поэтому
> можно взять что-то нейтральное — или просто остановиться на предпросмотре.

Напиши текст по правилам из `references/writing.md`, покажи, дождись согласия, опубликуй
с `--yes`, отдай ссылку из `permalink`.

## Этап 8. Итог

Отчитайся коротко, без пересказа JSON:

- аккаунт: `@username`;
- где лежат настройки, профиль голоса и очередь (пути из `$T config path`);
- токен действует до какой даты. Про продление скажи по факту: включено — `doctor` продлит
  сам; выключено — через 60 дней нужно выпустить новый маркер руками;
- лимиты, которые он выбрал;
- что можно попросить дальше: «напиши пост про…», «составь план на неделю», «что в комментариях»,
  «как зашёл вчерашний пост».

Если пользователь хочет, чтобы отложенные публикации уходили сами, объясни ограничение
(Threads API не умеет планировать, очередь локальная) и покажи `$T queue cron`.
Подробности — в `references/planning.md`.

## Если что-то пошло не так

| Симптом | Причина и что делать |
| --- | --- |
| Форма настроек не сохраняется: «Укажите URI переадресации для OAuth» | Поля с адресами нужны только для входа через браузер, которого в этом сценарии нет. Уйди со страницы, не сохраняя: генератору маркеров они не нужны. |
| В генераторе маркеров нет кнопки добавить аккаунт, либо маркер не выдаётся | Аккаунт Threads приватный. Маркеры выдаются только для общедоступных аккаунтов. |
| `me` работает, а публикация даёт 403 | Нет `threads_content_publish` в scope токена, либо аккаунт не принял приглашение тестировщика. Добавь разрешение в настройках приложения и выпусти маркер заново. |
| Пользователь сам прислал App Secret, хотя его не просили | Он не нужен — скажи об этом и не сохраняй. Если переписка где-то хранится, посоветуй перевыпустить секрет в дашборде. |

Остальные ошибки — в `references/troubleshooting.md`.
