# Контент-план и отложенные публикации

Читай, когда пользователь просит план, календарь, «что постить на неделю» или ставит
публикации на конкретное время.

---

## Главное ограничение

**Threads API не умеет отложенные публикации.** Ничего нельзя «поставить в Threads на завтра
на 9 утра» — платформа публикует только здесь и сейчас.

Поэтому очередь локальная: записи лежат в `queue.json` в профиле, и кто-то должен запустить
`queue run`. Варианты, от простого к надёжному:

1. **Ты запускаешь вручную** в следующей сессии: `$T queue run --yes`. Просто и предсказуемо,
   но публикация уйдёт тогда, когда пользователь позовёт тебя, а не в назначенное время.
2. **cron на машине пользователя**: `$T queue cron` печатает готовую строку и команду установки.
   Работает само — пока машина включена. Для ноутбука это значит «когда открыт».
3. **Постоянно включенный сервер** — тот же cron, но без пропусков.

Скажи это пользователю прямо, до того как он поверит в автопилот. Если ему нужна публикация
строго в 9:00 при выключенном ноутбуке — этот скилл такого не даёт, нужен внешний планировщик.

---

## Как строить план

План — это не 30 заголовков на месяц. Работающий план состоит из трёх частей.

### 1. Рубрики (2–4, не больше)

Повторяющиеся типы постов, по которым читатель узнаёт аккаунт. Выводи их из `voice.md`
и из того, что у пользователя уже зашло (`references/analytics.md`), а не из шаблонов.

Примеры формы, не содержания: «наблюдение из работы», «разбор ошибки», «короткий приём»,
«что читаю».

### 2. Ритм

Спроси и зафиксируй: сколько постов в неделю и в какие дни/часы. Не назначай пять постов в день
человеку, который постит дважды в неделю, — он забросит.

Разумный старт: 3–4 поста в неделю, из них одна цепочка. Лучше меньше и регулярно.

### 3. Банк идей

Список тем без дат — из него собираются недели. Пополняется из разговоров с пользователем,
его работы, комментариев под постами. Держи его в `plan.md` в профиле
(путь из `$T config path`), шаблон — `assets/plan.template.md`.

---

## Как собрать неделю

1. Прочитай `voice.md` и `plan.md`.
2. Посмотри, что уже публиковалось: `$T list --limit 20`. Не повторяй тему, которая была
   на прошлой неделе, и не ставь две однотипные подряд.
3. Предложи 3–5 позиций: дата, время, рубрика, **тезис поста одной строкой** — не готовый текст.
   Пользователю проще править план по тезисам.
4. Согласуй план. Дальше — пиши тексты по одному, а не все сразу: восемь черновиков
   за раз никто не вычитывает.
5. Согласованные тексты ставь в очередь.

Формат предложения плана — простая таблица, без украшений:

```
Пн 09:15  наблюдение     Почему я перестал измерять скорость сборки в секундах
Ср 09:15  разбор (цепь)  Три причины, по которым падал деплой, и что оказалось на самом деле
Пт 18:00  короткий приём Один флаг git, который экономит мне полчаса в неделю
```

## Работа с очередью

```bash
# Поставить пост на время (ISO-8601, обязательно с часовым поясом).
$T queue add --at 2026-10-02T09:15:00+03:00 --text "Текст поста" --note "рубрика: наблюдение"

# Поставить цепочку.
$T queue add --at 2026-10-04T09:15:00+03:00 --file chain.json

# Посмотреть.
$T queue list                 # всё
$T queue list --due           # чьё время уже пришло
$T queue list --status failed # что не ушло

# Удалить.
$T queue rm q_20261002T091500_0421

# Опубликовать наступившее.
$T queue run                  # предпросмотр: что уйдёт
$T queue run --yes            # публикация
$T queue run --yes --id q_…   # конкретную запись, не дожидаясь времени
```

Важное про очередь:

- Время указывай **с часовым поясом** пользователя (`defaults.timezone` в конфиге).
  Без смещения время считается UTC — легко промахнуться на несколько часов.
- Текст в очереди валидируется при добавлении (длина, стоп-слова, темы), а не при публикации.
  Ошибку увидишь сразу.
- `queue run` уважает те же лимиты `safety`, что и обычная публикация.
- Записи не исчезают: опубликованные помечаются `published` с ссылками, упавшие — `failed`
  с текстом ошибки. Разбирай `failed` в следующей сессии.
- Согласие пользователя нужно **на текст при постановке в очередь**. Отдельно спрашивать
  разрешение в момент `queue run` не нужно — оно уже получено. Но если текст лежал в очереди
  долго и мог устареть (новости, даты, «вчера»), перечитай его перед публикацией.

## Автозапуск через cron

```bash
$T queue cron
```

Отдай пользователю строку `install` и объясни: команда будет каждый час проверять очередь и
публиковать наступившее, лог — в `cron.log` рядом с профилем. Установку пользователь делает сам,
это изменение его системы — не запускай `crontab` за него без прямой просьбы.

Если пользователь согласился на cron, проверь, что `safety.require_yes_flag` не мешает: cron-строка
уже содержит `--yes`, то есть публикации будут уходить без участия человека. Убедись, что он
понимает это, и что в очереди только согласованные тексты.
