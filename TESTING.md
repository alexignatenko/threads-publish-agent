# Как проверить скилл на живом аккаунте

Порядок такой: сначала проверки без сети, потом чтение через API, и только в конце —
одна настоящая публикация. Между шагами ничего необратимого не происходит.

Если токен, который ты хочешь взять, **уже используется другим сервисом** — сначала прочитай
[«Общий токен с другим сервисом»](#общий-токен-с-другим-сервисом). Коротко: читать и публиковать
одним токеном из двух мест безопасно, опасно только автопродление, и его нужно выключить.

---

## Шаг 0. Проверки без сети

Запускается **из клона репозитория** — плагину клон не нужен, Claude Code стягивает
репозиторий в свой кэш сам. Клон нужен ровно для этих двух команд и для чтения кода.

Ничего не настраивая и не подключая:

```bash
python3 skills/threads-publishing/scripts/threads.py selftest
python3 tests/test_publish_flow.py
```

Оба должны закончиться успехом. Threads здесь не участвует вообще.

---

## Что именно ты тестируешь

Тестировать можно две разные вещи, и для них нужны разные настройки. Выбери до того,
как трогать токен.

| | **Путь CLI** | **Путь скилла** |
| --- | --- | --- |
| Что проверяется | Скрипт: запросы к API, лимиты, очередь | Поведение ИИ: онбординг, интервью о голосе, маршрутизация |
| Чем запускается | Ты руками в терминале | ИИ сам, через `Bash` |
| Откуда берётся `threads.py` | Из клона репозитория | Из кэша плагина |
| Профиль данных | Любой, можно изолированный | Только профиль по умолчанию |

**Главное, что легко упустить:** профиль выбирается переменной `THREADS_AGENT_HOME`
и флагом `--profile`. Если ты зададёшь их в своём терминале, ИИ об этом не узнает —
он запускает скрипт без `--profile`, то есть всегда работает с `~/.threads-agent`,
профиль `default`. Настроишь изолированный тестовый профиль — и ИИ скажет «не настроено»,
хотя ты только что всё настроила.

Отсюда два сценария:

- **Хочу проверить только скрипт** → шаг 1 ниже, изолированный профиль. ИИ в этом
  не участвует.
- **Хочу проверить скилл целиком** (ради этого он и сделан) → пропусти шаг 1 и используй
  профиль по умолчанию, чтобы вы с ИИ смотрели на одни и те же данные.

### Как отдать токен скиллу, не вставляя его в переписку

Экспортируй токен **до** запуска Claude Code — дочерние процессы его унаследуют,
и `Bash`-вызовы ИИ увидят переменную:

```bash
 export THREADS_ACCESS_TOKEN='твой_токен'    # пробел в начале: не попадёт в history
claude
```

Дальше в сессии скажи:

> Настрой публикации в Threads. Токен уже лежит в переменной окружения
> `THREADS_ACCESS_TOKEN`, в чат я его вставлять не буду. Продление токена выключи —
> этот же токен использует другой сервис.

Проверить, что всё сошлось, можно по `auth status`: в `from_env` должно быть
`["access_token"]`, а `credentials.json` остаться пустым.

Приятный побочный эффект: у токена из переменной нет метаданных о сроке жизни, поэтому
автопродление не сработает в принципе — даже до того, как ИИ выставит `allow_refresh=false`.

## Шаг 1. Отдельный профиль для тестов

**Нужен только для пути CLI.** Тестируешь скилл целиком — пропусти этот шаг.

Чтобы тестовый прогон не смешался с будущей рабочей настройкой, заведи отдельный профиль
и отдельный каталог данных:

```bash
export THREADS_AGENT_HOME=~/threads-test
T="python3 $PWD/skills/threads-publishing/scripts/threads.py --profile test"

$T config init
$T config path      # покажет, где всё лежит
```

Всё тестовое окажется в `~/threads-test/profiles/test/`. Когда закончишь — достаточно
удалить эту папку.

---

## Шаг 2. Отдать токен, ничего не записывая на диск

Самый аккуратный способ: передать токен переменной окружения. Он не попадёт ни в
`credentials.json`, ни в историю команд (если поставить пробел перед `export`).

```bash
 export THREADS_ACCESS_TOKEN='твой_токен'
```

Сразу выключи автопродление — это единственное, что вообще может повлиять на другой сервис:

```bash
$T config set auth.allow_refresh=false
```

Проверь, что скилл видит токен и понимает, что продлевать его нельзя:

```bash
$T auth status
$T doctor
```

Что ожидаемо увидишь:

- `auth status` → `from_env: ["access_token"]`, а `credentials.json` остался пустым: токен
  на диск не попал.
- `token_validity` → «срок неизвестен (токен передан через `THREADS_ACCESS_TOKEN`) —
  автопродление не сработает; оно и выключено в настройках». Это и нужно: срок жизни токена
  скилл не знает, поэтому продлевать не полезет, плюс явный запрет из настроек.
- `voice: ok=false` — профиль голоса ещё шаблон, для теста не мешает.

## Шаг 3. Только чтение

Ни одна из этих команд ничего не меняет в аккаунте:

```bash
$T me                      # тот ли аккаунт? посмотри username
$T quota                   # сколько постов и ответов осталось за сутки
$T list --limit 5          # последние посты
$T insights --media-id <ID из list>
```

**Проверь `username` в `me`.** Это единственный момент, когда ошибку с аккаунтом ещё можно
поймать до публикации.

Если `quota` или `insights` дают 403 — у токена нет нужных разрешений
(`threads_content_publish`, `threads_manage_insights`). Чтение постов при этом работает.
Это нормально и ожидаемо для токена, выданного под другие задачи.

---

## Шаг 4. Предпросмотр публикации — по-прежнему без записи

```bash
$T post --text "Проверка агента. Этот пост скоро удалю."
```

Команда **не делает ни одного запроса к API** — только показывает, что ушло бы:

```json
{
  "published": false,
  "dry_run": true,
  "would_send": { "media_type": "TEXT", "text": "…", "reply_control": "everyone" }
}
```

Посмотри на `would_send` — это буквально параметры будущего запроса. Проверь и цепочку:

```bash
$T chain --file skills/threads-publishing/assets/chain.example.json
```

---

## Шаг 5. Одна настоящая публикация

Дальше — необратимо. **Threads API не умеет удалять и редактировать посты**: удалить
получится только руками в приложении Threads.

```bash
$T post --text "Проверка публикации через API." --yes
```

В ответе смотри `"published": true` и `permalink` — открой ссылку, убедись, что пост на месте
и в нужном аккаунте. Потом удали его руками в приложении, если он не нужен.

Если что-то пошло не так, читай `hint` в ответе и
`skills/threads-publishing/references/troubleshooting.md`.

---

## Шаг 6. Очередь

```bash
$T queue add --at 2020-01-01T00:00:00Z --text "Проверка очереди"
$T queue list --due      # запись видна, время «пришло»
$T queue run             # предпросмотр, ничего не публикует
$T queue rm <id>         # убрать, не публикуя
```

`queue run --yes` опубликует по-настоящему — запускай только если хочешь второй живой пост.

---

## Шаг 7. Убрать за собой

```bash
rm -rf ~/threads-test
unset THREADS_AGENT_HOME THREADS_ACCESS_TOKEN
```

Опубликованные посты удаляются только вручную в приложении Threads.

После этого можно настраивать по-настоящему: `/threads:setup` или «настрой публикации в Threads».

## Общий токен с другим сервисом

### Что безопасно

**Читать и публиковать одним токеном из двух мест — безопасно.** Токен Threads не одноразовый,
обращения к API его не расходуют и не аннулируют. Два сервиса с одной строкой токена
не мешают друг другу.

### Что может помешать

| Риск | Насколько вероятно | Что делать |
| --- | --- | --- |
| **Продление токена** (`refresh_access_token`) выдаёт новую строку. По наблюдениям старая продолжает работать, но Meta этого прямо не гарантирует. | Низкий, но не нулевой | `$T config set auth.allow_refresh=false`. Тогда ни `doctor`, ни `auth ensure`, ни `auth refresh` токен не тронут. |
| **Суточная квота общая на профиль**: 250 постов и 1000 ответов за 24 часа делятся между всеми приложениями. | Реально, если другой сервис постит много | `$T quota` показывает настоящий расход по профилю. Локальный `safety.max_posts_per_day` считает только свои посты и про чужие не знает. |
| **Смена Redirect URI в настройках приложения Meta** сломает OAuth у другого сервиса. | Высокий, если полезть в настройки | Не меняй существующий. Meta разрешает несколько адресов — **добавляй**, а не заменяй. Локальная команда `auth set-app --redirect-uri` пишет только в свой конфиг и на настройки Meta не влияет. |
| **Отзыв доступа** в Threads → Настройки → Сайты и приложения убивает **все** токены этого приложения. | Только если сделать это вручную | Не отзывай доступ, пока другой сервис работает. |
| **`auth save-token`** по умолчанию пытается обменять токен на 60-дневный, то есть выпустить новую строку. | Средний | Для общего токена передавай `--no-exchange`, либо вообще не сохраняй токен на диск — используй `THREADS_ACCESS_TOKEN`, как в шаге 2. |

### Если хочется полной изоляции

Создай **отдельное приложение** в Meta for Developers для тестов и выпусти в нём свой токен.
Тогда пересечений с работающим сервисом нет вообще: токены привязаны к приложению, квота
на публикацию всё равно общая на профиль Threads, но всё остальное независимо.
Это 10–15 минут — см. `skills/threads-publishing/references/setup.md`, этап 3.

Сводка: для быстрой проверки хватит существующего токена с `auth.allow_refresh=false`.
Для постоянной работы лучше отдельное приложение — иначе однажды кто-то из двух сервисов
продлит токен, и придётся вспоминать, почему второй отвалился.
